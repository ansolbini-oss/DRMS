## 1. 도메인 모델

### 1.1 사업자 : 사업장 = 1 : N

- **사업자(법인)**: 사업자번호(BRN) 단위. DRMS의 모든 목록은 사업자 단위로 노출.
- **사업장(KEPCO 미터링 단위)**: 한 사업자가 하나 이상의 사업장을 보유. 계약·정산·자원 매핑은 사업장 단위.

### 1.2 사업장 단위 계약상태 — 3개 명시 상태

`siteStatus` 필드 (사업장 entity)

| 값 | 의미 | 진입 트리거 |
|---|---|---|
| `계약대기` | 사전검증은 완료, 계약 체결 전 | 사전검증 → 계약 전환 시 자동 부여 |
| `계약완료` | 계약기간·수수료 입력 완료, 활성 계약 중 | 계약기간·수수료 입력 시 자동 부여 |
| `계약만료` | 계약기간 종료 | `today > endDate` 시 자동 부여 |

### 1.3 사업자 단위 종합 상태 — 저장하지 않음, 파생 계산

사업자 row 표기는 **사업장 siteStatus 집계로 매번 계산** (`ctComputeBizStatus`).

| 우선순위 | 종합 상태 | 조건 |
|:---:|---|---|
| 1 | **계약대기** | 사업장 중 `계약대기`가 1개 이상 |
| 2 | **계약만료** | 모든 사업장이 `계약만료` (활성 사업장 0) |
| 3 | **계약완료** | 그 외 (활성 사업장 ≥ 1, 대기 0) |

→ "계약진행" 같은 중간 상태는 별도로 두지 않음. 명시적 3상태로 통일.

### 1.4 만료 예정(Expiring Soon)

- 별도 상태가 아닌 **부가 표기**.
- 조건: `siteStatus = 계약완료` AND `endDate ≤ today + 60일`
- 표기:
  - 사업자 단위 종합 뱃지 옆에 ⚠️ 아이콘 (텍스트 없음, hover로 건수 노출)
  - KPI 카드 "만료 예정" 카운트에 포함
- 자동 소멸: 그 사업장이 실제 만료되면 다른 활성 사업장 기준으로 사업자 종합 상태가 재계산되며 ⚠️ 칩도 자연 소멸.

## 2. 상태 전이 흐름

### 2.1 자동 전이 (시스템 기본 동작)

```
[사전검증 완료]
      ↓ 계약 전환
  계약대기  ──(계약기간·수수료 입력)──▶  계약완료  ──(today > endDate)──▶  계약만료
```

- 운영자가 가만히 있어도 자연스럽게 굴러감.
- 계약기간 만료 시점은 목록·상세 진입 시점에 재계산 (배치 불필요).

### 2.2 운영자 직접 변경 (Manual Override)

사업장 정보 영역의 **계약상태 드롭다운**에서 운영자가 언제든 직접 선택 가능.

| 시나리오 | 변경 흐름 |
|---|---|
| 재계약 (만료 → 재계약) | 만료 사업장의 계약상태를 **계약대기**로 되돌림 → 새 계약기간·수수료 입력 → **계약완료**로 다시 자동 전환 |
| 사전검증 미진행 사업장 외부 관리 | (예외) **계약완료**로 직접 지정 (감사로그 기록) |
| 운영자 실수 정정 | 어느 상태로든 강제 변경 가능 |

**원칙**:
- 운영자가 명시적으로 변경한 `siteStatus`는 자동 흐름이 덮어쓰지 않음.
- 모든 변경은 감사로그에 기록 (`site_status_changed`).
- 변경 즉시 사업자 종합 상태·KPI·목록이 재계산.

## 3. 화면 표기 규칙

### 3.1 계약관리 목록 (5칼럼)

| 칼럼 | 내용 |
|---|---|
| 사업자명 | `c.name` |
| 사업자번호 | `c.bizno` (10자리 BRN, monospace) |
| 사업장 수 | `c.sites.length`개 |
| 계약상태 | 종합 상태 뱃지 + (해당 시) ⚠️ 만료 예정 아이콘 |
| 상세보기 | 버튼 → 상세 페이지 진입 |

- 접수번호(`recno`)·KEPCO 고객번호는 목록에서 제거. 상세 페이지·사업장 확장 row에서 노출.

### 3.2 KPI 카드 (5개)

| 카드 | 카운트 산식 |
|---|---|
| 전체 계약 대상 | `ctEligibleCustomers().length` |
| 계약대기 | 종합 상태 = `계약대기` 사업자 수 |
| 계약완료 | 종합 상태 = `계약완료` 사업자 수 |
| 만료 예정 | `biz.expiringCount > 0` 사업자 수 |
| 계약만료 | 종합 상태 = `계약만료` 사업자 수 |

### 3.3 필터 (계약상태 select)

옵션: `계약대기` / `계약완료` / `계약만료` 3개. 만료 예정은 별도 토글로 분리 권장(추후).

### 3.4 사업장 확장 row — 사업장 정보 테이블

라벨좌(회색·중앙) / 값우 형태, 8개 행:

```
사업장명 · 담당자 · 담당자 연락처 · 주소 · 계약기간 · 계약전력 · 수수료 · 계약상태(드롭다운)
```

계약상태 row만 인터랙티브: `<select>` 변경 즉시 저장.

## 4. 데이터 모델 변경사항 (백엔드 적용 시)

### 4.1 사업장 엔티티에 필드 추가

```jsonc
{
  "id": "C1001-S1",
  "siteName": "강남 사업장",
  // ... 기존 필드
  "siteStatus": "계약완료",   // 신규: '계약대기' | '계약완료' | '계약만료'
  "contract": {
    "startDate": "2024-03-01",
    "endDate": "2025-02-28",
    "power": 1200,
    "feeRate": 4.0,
    "docs": { ... }
  }
}
```

### 4.2 사업자 엔티티에서 제거(또는 유지하되 derive)

- `c.contractStage` — 더 이상 사용 안 함. 마이그레이션 시 제거 권장.
- `c.status` (`검증완료`/`계약완료`/`반려`) — 사전검증 단계 상태로만 의미 유지. 계약관리에선 참조 안 함.

### 4.3 마이그레이션 시 자동 부여 규칙

기존 사업장에 `siteStatus`가 없을 때:

```
if (contract.startDate && contract.endDate)
   siteStatus = (today > endDate) ? '계약만료' : '계약완료'
elif (c.status === '반려')
   siteStatus = '계약만료'
else
   siteStatus = '계약대기'
```

(현재 mockup의 `ctEnsureCustomerMeta` 동일 로직)

### 4.4 감사 로그 이벤트

| action | object | desc 예시 |
|---|---|---|
| `site_status_changed` | site | `계약완료 → 계약대기 (삼성전자)` |
| `site_added` | site | `신규 사업장 1 (삼성전자)` |
| `site_deleted` | site | `(삼성전자)` |

## 5. API 힌트 (백엔드 인터페이스)

```
PATCH /sites/{siteId}/status
  body: { status: '계약대기' | '계약완료' | '계약만료' }
  response: { siteStatus, bizStatus, expiringCount, updatedAt }

GET /customers?stage=계약대기
  query: stage=계약대기|계약완료|계약만료, expiring=true|false
  response: 종합 상태 파생값 포함
```

- `PATCH /sites/.../status` 응답에 사업자 종합 상태도 동봉하면 프론트에서 별도 재조회 불필요.

## 6. 결정 근거 (FAQ)

**Q1. 왜 사업자 종합 상태를 저장하지 않고 매번 계산하나?**
A. 사업장 만료일 도래 시 자동 전환을 위한 배치/트리거 불필요. 데이터 정합성 유지가 단순함. 사업장 N개 집계는 O(N)이며 N이 작아 성능 영향 미미.

**Q2. "만료 예정"을 별도 상태로 두지 않은 이유?**
A. 시간이 지나면 자동 만료 상태로 전환되어야 하는데, 상태로 두면 또 다른 전환 트리거가 필요. 부가 표기(⚠️ 아이콘)로만 두면 사업장 만료 시점에 자연스럽게 소멸.

**Q3. 운영자 manual override 후 자동 흐름은?**
A. `siteStatus`가 명시적으로 세팅되어 있으면 자동 부여 로직(`if(s.siteStatus) return`)에서 스킵. 다만 `today > endDate` 자동 만료는 매번 진입 시 재평가하지 않음 — 현재 mockup은 진입 시점 한 번만 부여. 백엔드 적용 시 배치 또는 read-time 재계산 정책 결정 필요.

**Q4. 재계약 시 동일 사업장 ID 유지 vs 신규 사업장 생성?**
A. 동일 사업장 ID 유지 + 계약기간·수수료 갱신을 권장. 사전검증 이력·KEPCO 미터링 매핑·자원관리 연계가 끊기지 않음.
