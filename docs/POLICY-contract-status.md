## 1. 도메인 모델

### 1.1 사업자 : 사업장 = 1 : N

- **사업자(법인)**: 사업자번호(BRN) 단위. DRMS의 모든 목록은 사업자 단위로 노출.
- **사업장(KEPCO 미터링 단위)**: 한 사업자가 하나 이상의 사업장을 보유. 계약·정산·자원 매핑은 사업장 단위.

### 1.2 사업장 단위 계약상태 — 4개 명시 상태

`siteStatus` 필드 (사업장 entity)

| 값 | 의미 | 진입 트리거 | 자동/수동 |
|---|---|---|:---:|
| `계약대기` | 사전검증은 완료, 계약 체결 전 | 사전검증 → 계약 전환 시 자동 부여 | 자동 |
| `계약완료` | 계약기간·수수료 입력 완료, 활성 계약 중 | 계약기간·수수료 입력 시 자동 부여 | 자동 |
| `계약만료` | 계약기간 자연 종료 | `today > endDate` 시 자동 부여 | 자동 |
| `계약해지` | 계약기간 도래 전 중도 종료 | 운영자가 사업장 정보 드롭다운에서 직접 선택 | **수동 전용** |

> **`계약만료` vs `계약해지` 차이**
> - 계약만료: 정상 lifecycle 종료 (계약기간 자연 만료)
> - 계약해지: 비정상 종료 (위약·합의·고객사 폐업 등 중도 종료)

### 1.3 사업자 단위 종합 상태 — 저장하지 않음, 파생 계산

사업자 목록 표기는 **사업장 siteStatus 집계로 매번 계산** (`ctComputeBizStatus`).

| 우선순위 | 종합 상태 | 조건 |
|:---:|---|---|
| 1 | **계약대기** | 사업장 중 `계약대기`가 1개 이상 |
| 2 | **계약해지** | 모든 사업장이 `계약해지` |
| 3 | **계약만료** | 모든 사업장이 `계약만료` (활성 사업장 0) |
| 4 | **계약완료** | 그 외 (활성 사업장 ≥ 1, 대기 0) |

→ 종합 상태는 별도 저장 없이 매번 산출. 시간 경과로 자동 만료된 사업장도 즉시 반영.

### 1.4 만료 예정(Expiring Soon)

- 별도 상태가 아닌 **부가 표기**.
- 조건: `siteStatus = 계약완료` AND `endDate ≤ today + 60일`
- 표기 위치: **목록 테이블의 `계약완료` 칼럼 셀**에 ⚠️ 아이콘 (호버 시 "만료 예정 N건 (60일 내 종료)" 툴팁)
- 의미: "이 사업자의 계약완료 사업장 중 일부가 60일 내 만료될 예정 — 재계약 협의 필요"
- 자동 소멸: 그 사업장이 실제 만료되면 `계약만료`로 자동 이동, ⚠️ 시그널 자연 소멸.

## 2. 상태 전이 흐름

### 2.1 자동 전이 (시스템 기본 동작)

```
[사전검증 완료]
      ↓ 계약 전환
  계약대기 ──(계약기간·수수료 입력)──▶ 계약완료 ──(today > endDate)──▶ 계약만료
```

- 운영자가 손대지 않아도 자연스럽게 굴러감.
- 계약기간 만료 시점은 목록·상세 진입 시점에 재계산 (배치 불필요).
- `계약해지`는 자동 전이 경로에 없음 — 운영자 수동 선택에만 진입.

### 2.2 운영자 직접 변경 (수동 변경 / Manual Override)

사업장 정보 영역의 **계약상태 드롭다운**에서 운영자가 언제든 직접 선택 가능. 4개 옵션 모두 선택 가능.

| 시나리오 | 변경 흐름 |
|---|---|
| 재계약 (만료 → 재계약) | 만료 사업장의 계약상태를 **계약대기**로 되돌림 → 새 계약기간·수수료 입력 → **계약완료**로 다시 자동 전환 |
| 중도 해지 | **계약해지** 직접 선택 (위약·합의·고객사 폐업 등) |
| 사전검증 미진행 사업장 외부 관리 | (예외) **계약완료**로 직접 지정 |
| 운영자 실수 정정 | 어느 상태로든 강제 변경 가능 |

**원칙**:
- 운영자가 명시적으로 변경한 `siteStatus`는 자동 흐름이 덮어쓰지 않음.
- 모든 변경은 감사로그에 기록 (`site_status_changed`).
- 변경 즉시 사업자 종합 상태·KPI·목록이 재계산.

## 3. 화면 표기 규칙

### 3.1 계약관리 목록 (8칼럼)

| # | 칼럼 | 내용 | 비고 |
|:---:|---|---|---|
| 1 | 사업자명 | `c.name` | 클릭 시 상세 진입 |
| 2 | 사업자번호 | `c.bizno` (10자리 BRN, monospace) | 사업자 고유 식별자 |
| 3 | 사업장 수 | `c.sites.length`개 | 사업자 보유 사업장 총수 |
| 4 | 계약대기 | `siteStatus = 계약대기` 사업장 수 | amber 색상 강조 |
| 5 | 계약완료 | `siteStatus = 계약완료` 사업장 수 + (해당 시) ⚠️ | green 색상 강조. ⚠️는 만료 예정 시그널 |
| 6 | 계약만료 | `siteStatus = 계약만료` 사업장 수 | text-sub 색상 |
| 7 | 계약해지 | `siteStatus = 계약해지` 사업장 수 | red 색상 (중도 종료 시그널) |
| 8 | 상세보기 | 버튼 → 상세 페이지 진입 | — |

- 0인 셀은 `—` 표기 (시각적 노이즈 최소화)
- 접수번호·KEPCO 고객번호는 목록에서 제외, 상세에서 노출
- **상태별 카운트의 합 = 사업장 수** (정합성 보장)

### 3.2 KPI 카드 (5개) — 현황카드 운영 기준

| 카드 | 카운트 산식 | 운영 의미 | 운영자 액션 |
|---|---|---|---|
| 전체 계약 대상 | `ctEligibleCustomers().length` | 사전검증 완료/계약 처리 이력 보유 사업자 총수 | 모니터링 |
| 계약대기 | 종합 상태 = `계약대기` 사업자 수 | 사전검증 후 계약 미체결 사업자 | 계약기간·수수료 입력 진행 |
| 계약완료 | 종합 상태 = `계약완료` 사업자 수 | 활성 계약 중 — 자원관리 매핑 가능 | 모니터링 |
| 만료 예정 | `biz.expiringCount > 0` 사업자 수 | 60일 내 만료될 사업장 보유 사업자 | **재계약 협의 시작** |
| 계약만료 | 종합 상태 = `계약만료` 사업자 수 | 모든 사업장 계약 종료 | 재계약 검토 또는 종결 |

> KPI 카드 클릭 시 해당 상태로 필터링되는 인터랙션은 추후 추가 권장.
> `계약해지`는 별도 카드 없음 — 비정상 종료 케이스라 KPI 트래킹보다 감사 추적이 중요.

### 3.3 필터 (계약상태 select)

옵션 4개: `계약대기` / `계약완료` / `계약만료` / `계약해지`

- "만료 예정"은 현재 별도 토글 없음 — KPI 카드와 목록 ⚠️ 아이콘으로 식별. 별도 토글 분리는 추후 검토.

### 3.4 사업장 확장 row — 사업장 정보 테이블

라벨좌(회색·중앙) / 값우 형태, 8개 행:

```
사업장명 · 담당자 · 담당자 연락처 · 주소 · 계약기간 · 계약전력 · 수수료 · 계약상태(드롭다운)
```

- 계약상태 row만 인터랙티브: `<select>` 옵션 4개 (대기/완료/만료/해지)
- 변경 즉시 저장 + 토스트 + 감사로그

## 4. 데이터 모델 변경사항 (백엔드 적용 시)

### 4.1 사업장 엔티티에 필드 추가

```jsonc
{
  "id": "C1001-S1",
  "siteName": "강남 사업장",
  // ... 기존 필드
  "siteStatus": "계약완료",   // '계약대기' | '계약완료' | '계약만료' | '계약해지'
  "contract": {
    "startDate": "2024-03-01",
    "endDate": "2025-02-28",
    "power": 1200,
    "feeRate": 4.0,
    "docs": { ... }
  }
}
```

### 4.2 사업자 엔티티에서 제거(또는 유지하되 derive)

- `c.contractStage` — 더 이상 사용 안 함. 마이그레이션 시 제거 권장.
- `c.status` (`검증완료`/`계약완료`/`반려`) — 사전검증 단계 상태로만 의미 유지. 계약관리에선 참조 안 함.

### 4.3 마이그레이션 시 자동 부여 규칙

기존 사업장에 `siteStatus`가 없을 때:

```
if (contract.startDate && contract.endDate)
   siteStatus = (today > endDate) ? '계약만료' : '계약완료'
elif (c.status === '반려')
   siteStatus = '계약만료'
else
   siteStatus = '계약대기'
```

- `계약해지`는 마이그레이션 자동 부여 대상 아님 (운영자 수동 전용)
- (현재 mockup의 `ctEnsureCustomerMeta` 동일 로직)

### 4.4 감사 로그 이벤트

| action | object | desc 예시 |
|---|---|---|
| `site_status_changed` | site | `계약완료 → 계약해지 (LG전자 평택 LG공장)` |
| `site_added` | site | `신규 사업장 1 (삼성전자)` |
| `site_deleted` | site | `(삼성전자)` |
| `customer_info_updated` | customer | 변경 필드 diff |

`계약해지` 사유는 별도 메모(`store.memos[c.recno]`)에 기록 권장 — 감사 추적·후속 정산 분쟁 대비.

## 5. API 힌트 (백엔드 인터페이스)

```
PATCH /sites/{siteId}/status
  body: { status: '계약대기' | '계약완료' | '계약만료' | '계약해지', reason?: string }
  response: { siteStatus, bizStatus, expiringCount, updatedAt }

GET /customers?stage=계약대기
  query: stage=계약대기|계약완료|계약만료|계약해지, expiring=true|false
  response: 종합 상태 파생값 + counts(상태별 사업장 수) + expiringCount 동봉
```

- `PATCH /sites/.../status`에 `reason` 옵셔널 파라미터 — 특히 `계약해지` 시 필수 권장
- 응답에 사업자 종합 상태·counts·expiringCount 동봉하면 프론트 별도 재조회 불필요

## 6. 결정 근거 (FAQ)

**Q1. 왜 사업자 종합 상태를 저장하지 않고 매번 계산하나?**
A. 사업장 만료일 도래 시 자동 전환을 위한 배치/트리거 불필요. 데이터 정합성 유지가 단순함. 사업장 N개 집계는 O(N)이며 N이 작아 성능 영향 미미.

**Q2. "만료 예정"을 별도 상태로 두지 않은 이유?**
A. 시간이 지나면 자동 만료 상태로 전환되어야 하는데, 상태로 두면 또 다른 전환 트리거가 필요. 부가 표기(⚠️ 아이콘)로만 두면 사업장 만료 시점에 자연스럽게 소멸. 또한 만료 예정 사업장은 아직 `계약완료` 상태이므로 `계약완료` 칼럼에 표기되는 게 의미상 정확.

**Q3. `계약해지`를 자동 부여 안 하는 이유?**
A. 해지는 비즈니스 협의·법적 절차가 동반되는 액션. 시스템이 자동 판단할 수 없는 의사결정이므로 운영자 수동 선택만 허용. 또한 해지 사유 기록(메모·감사로그)도 운영자 책임.

**Q4. 운영자 manual override 후 자동 흐름은?**
A. `siteStatus`가 명시적으로 세팅되어 있으면 자동 부여 로직(`if(s.siteStatus) return`)에서 스킵. 다만 `today > endDate` 자동 만료는 매번 진입 시 재평가하지 않음 — 현재 mockup은 진입 시점 한 번만 부여. 백엔드 적용 시 배치 또는 read-time 재계산 정책 결정 필요.

**Q5. 재계약 시 동일 사업장 ID 유지 vs 신규 사업장 생성?**
A. 동일 사업장 ID 유지 + 계약기간·수수료 갱신을 권장. 사전검증 이력·KEPCO 미터링 매핑·자원관리 연계가 끊기지 않음. 단 `계약해지` 후 재계약은 신규 ID로 추적해야 감사 흐름이 명확.

**Q6. 종합 상태 우선순위에서 "계약해지"가 "계약만료"보다 우선인 이유?**
A. 둘 다 비활성(전체 사업장 종료) 상태지만, 해지는 비정상 종료라 시그널 강도가 더 높음. 모든 사업장이 해지된 사업자는 운영자 후속 액션(정산·법적 절차)이 필요할 가능성이 높아 우선 노출.
